# Spike 16: Tauri 2 shell as a native Windows executable

Replaces the paused Linux "Tauri shell + AppImage" idea. Proves one thing: a minimal Tauri 2 app
bundles into a native Windows `.exe` installer, installs, and runs as a real window that loads only
bundled assets. Issue #26.

This is a shell spike, not the app: one window, static placeholder page, no commands, no plugins,
no capture, no overlay, no provider code.

## Layout

| Path | Purpose |
|---|---|
| `src/main.rs`, `build.rs`, `Cargo.toml` | Tauri 2 Rust shell (nothing but `tauri::Builder::default().run(...)`) |
| `tauri.conf.json` | One window; `frontendDist: ./ui`; **no `devUrl`**; strict CSP; NSIS + MSI targets |
| `capabilities/default.json` | Empty permission set (the page can call no commands) |
| `ui/` | Static HTML/CSS/JS, no bundler, no dev server, no network resources |
| `icons/` | Placeholder icons generated by `tauri icon` from `icons/source.png` (a plain orange ring, not a brand asset) |
| `package.json` | Pins `@tauri-apps/cli` (local devDependency); no other JS dependency |
| `verify.ps1` | Launches an exe; checks the window and the process tree's network endpoints |

## Build

From Windows PowerShell with the repo on a UNC path:

```powershell
$env:CARGO_TARGET_DIR = "$env:TEMP\aeye-target-16"      # dodges the UNC incremental-lock bug
Set-Location '\\wsl$\Ubuntu\home\usaas\projects\code\A-Eye-worktrees\packaging\spikes\part-16-windows-shell'
npm install                                              # works over UNC (2 packages)
node node_modules\@tauri-apps\cli\tauri.js build         # NOT `npm run tauri` / `npx`, see below
```

UNC deviations found:

- `npm install` over the UNC path worked; no local checkout was needed.
- `npx tauri` / `npm run tauri` fail: they go through `cmd.exe`, which refuses a UNC working
  directory ("UNC paths are not supported. Defaulting to Windows directory") and the CLI then cannot
  find `tauri.conf.json`. Calling the CLI's JS entry with `node` directly works.
- `cargo tauri` was not used (that needs a global `cargo install tauri-cli`).

Output (under `$env:CARGO_TARGET_DIR\release`, ~1m50s cold build):

## Verification

```powershell
powershell -ExecutionPolicy Bypass -File verify.ps1 -Exe <exe> -Screenshot <png>
```

Proven on this machine (Windows desktop, 2026-10-18):

- **Standalone exe** launches: `MainWindowHandle` non-zero, `MainWindowTitle` = `A-Eye Spike 16`,
  window visible.
- **NSIS installer** (`/S`, per-user, no admin) installed to `%LOCALAPPDATA%\A-Eye Spike 16`, wrote an
  uninstall registry entry; the installed exe launched the same way in 4 further valid runs; `uninstall.exe /S`
  removed the install dir and registry entry.
- **Window content** (screenshot, inspected by eye): "Hello from A-Eye" rendered, and the page reports
  its own origin as `http://tauri.localhost/` (no port).
- **No web server / no LAN listener**: in the app process plus its 6 `msedgewebview2.exe` descendants,
  0 TCP sockets in any state (so no listener on `0.0.0.0`, `::` or loopback), and no new system-wide
  TCP listener appeared after launch. The release build serves `ui/` from the binary through
  WebView2's in-process custom-protocol virtual host; no dev server is involved (`tauri.conf.json`
  has no `devUrl`, and no `tauri dev` was run).

### Finding: one intermittent WebView2 UDP socket

In two of the first three launches of the standalone exe, the tree owned one UDP endpoint bound to the IPv6
wildcard on an ephemeral port (`:::54611`, later `:::60972`). It belonged to WebView2's Chromium
network service (`msedgewebview2.exe --utility-sub-type=network.mojom.NetworkService`), not to our code.
It stayed for the life of the process (checked for 28 s). The third standalone launch and the four
installed launches did not show it, so its trigger is unknown. It is not HTTP and cannot serve a page to a browser,
but a wildcard-bound UDP socket is technically LAN-addressable. Unverified: what triggers it,
whether it accepts inbound datagrams from the LAN, and whether `additionalBrowserArgs` can suppress
it. Treat "no UDP endpoint" as **not** proven; "no TCP listener / no web server" is.

`verify.ps1` therefore gates on TCP and only reports UDP.

## Not verified

- **MSI** was built but not installed or run (a per-machine MSI needs admin; not attempted).
- **Signing**: both installers are unsigned (`Get-AuthenticodeSignature` = `NotSigned`); SmartScreen
  behaviour untested.
- **Clean machine**: WebView2 runtime was already present; `webviewInstallMode: skip` means the
  installers do not install it. A clean-machine install is untested.
- Mixed-DPI / multi-monitor window placement, upgrade-in-place, uninstall while running.
- `%LOCALAPPDATA%\dev.aeye.spike16\EBWebView` (WebView2 profile) is left behind after uninstall; the
  silent uninstall did not remove it.
- One `verify.ps1` run (installed exe, `-SettleSec 8`) reported 134 TCP and 89 UDP sockets "owned by
  the tree" including system services, and was then killed (exit 137). I could not reproduce it in 4
  later runs; I treat it as a script fault, discarded it, and hardened the tree walk (PID-reuse
  guard) afterwards, but the cause is **not** established.
- Tauri vs Electron comparison, idle memory and startup time (STACK.md Phase 0) were not measured.
- Placeholder icons and the identifier `dev.aeye.spike16` are not product decisions.
